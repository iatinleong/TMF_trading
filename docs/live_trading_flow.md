# 現在的量化交易流程（2026-08-30 現況）

> 這份文件描述「現在程式碼實際在做的事」，寫給要快速搞懂整個流程、或之後要
> 交接/回顧用。逐條對照過 `backend/strategy_service.py` 的實際實作，不是憑
> 印象寫的設計文件。細節/踩過的坑另見 `docs/order_execution_logic.md`。

## 0. 大架構

4 個獨立方向策略，可同時勾選啟用：

| strategy_id | 策略 | 方向限定 |
|---|---|---|
| `breakout_long` | 突破 | 只做多 |
| `breakout_short` | 突破 | 只做空 |
| `pullback_long` | 回測（pullback） | 只做多 |
| `pullback_short` | 回測（pullback） | 只做空 |

每支策略各自用 `StrategyState` 記自己的倉位（`held_qty`/`held_direction`/
`entry_price`），彼此獨立風控、獨立判斷進出場，互不干擾。背景 `strategy_loop`
**每 60 秒**呼叫一次 `strategy_tick()`，依序處理所有已啟用的策略。

**為什麼必須有內部記帳？**
當多支策略同時交易同一個商品（例如 `breakout_long` 與 `pullback_long` 先後做多 `TM09` 各 1 口），券商主機只會回報合併後的淨部位（如「`TM09 多 2 口，均價 46100`」）。券商資料完全沒有記錄這兩口各自是誰的。程式必須靠各策略自己的 `StrategyState`，才能精確記住各自真正的進場成本（如 46000 vs 46200）、掛出各自專屬的 OCO 智慧單，並在出現反向訊號時「只平掉屬於自己的那 1 口」，不會搶平別人的部位。

K 棒是 **60 分鐘**線，訊號（MA5/MA20/MA60 交叉、回測拉回）在 K 棒**收盤**那一刻
才算數。K 棒資料由即時 tick 合成並落地快取；另有背景安全網（`shioaji_backfill.py`）每 300 秒自動檢查並回補過去 2 天歷史缺口，確保盤中重開後 5/20/60MA 均線計算不失真。

---

## 1. 訊號確認 → 進場，時機怎麼算

**不是等下一根 K 棒收盤、用它的開盤價成交**——比較精確的說法是：

1. 某根 60 分鐘 K 棒收盤時，`generate_breakout_signals`/`generate_pullback_signals`
   算出這根收盤確認一個訊號（`_signaled_frame`）。
2. `_latest_closed_signal()` 固定看「倒數第二根」（最後一根可能還在成形中，不
   採用），如果那根有訊號，回傳它。
3. 策略每 60 秒的檢查（`_tick_one`）發現這是一個**還沒消費過**的新訊號
   （拿 `bar_time + direction` 組出來的 key 跟 `state.last_signal_key` 比對）
   → **立刻用市價單（FOK）進場**，不等下一根收盤、不等特定開盤價格式，成交
   價用「當下最新報價」估計。

實務上：訊號在某根 K 棒收盤確認 → **最晚 60 秒內**（下一次 tick）就會被偵測
到並進場，用的是進場當下的即時報價，不是理論上「下一根開盤價」那個精確
數字（回測引擎 `backtest_engine.py` 才是真的模擬下一根開盤價成交，實盤跟
回測在「進場價格怎麼算」這件事上不是 100% 一致，這是兩者的已知差異）。

**同向訊號不加碼**：已經持倉的方向，同向訊號出現不會動作（`state.held_qty>0`
時直接略過）。**方向限定**：`breakout_long` 只認多方訊號，出現空方訊號時
如果手上有多單就平倉出場，手上沒有部位則什麼都不做（不會反手做空）。

## 2. 進場成交後：估算成交價

```python
entry_px = float(quote) if quote else 0.0     # 優先：進場當下的即時報價
if entry_px <= 0:
    # 2026-08-30 加固：即時報價缺失時（連線瞬斷等情況），依序退回
    entry_px = <broker 下單後刷新快照裡，這個商品的實際持倉均價>   # 次選
    entry_px = <最新收盤 K 棒的收盤價>                              # 最後備援
```

三層備援確保 `entry_price` 幾乎不可能停在 0——這件事很重要，因為
`entry_price>0` 是下一步「掛真實保護單」的前提條件，見下一節。

---

## 3. 進場成交後：立刻掛真實保護單（OCO）

`entry_price>0` 就會呼叫 `_place_oco_protection_for_state()`，用
`SendFutureOCOOrderV1` **一次委託同時掛停損＋停利兩支腿**：

- 多單：停損＝進場價－100 點，停利＝進場價＋250 點（賣出平倉）
- 空單：停損＝進場價＋100 點，停利＝進場價－250 點（買進平倉）

這是掛在**券商端**的真實委託，跟我們的軟體有沒有在跑無關——就算後端程式
當掉、電腦重開機，這張單還是活的。（為什麼是「一次委託兩支腿」而不是分開
掛 STP+MIT 兩張，見 `order_execution_logic.md` §3/§7——分開掛會被券商拒絕
第二張。）

**平倉防呆特性**：OCO 委託參數一律指定 `new_close = 1（平倉）`。依期交所與券商結算規則，這張單子只能用來抵銷已有部位；若部位已在其他地方平倉，觸發時券商主機會直接拒單（「留倉部位不足」），**絕不可能意外反手開出全新部位**。

**這一步可能失敗**（非 TMF 具體月份商品、券商拒單、送單例外），失敗的話
`state.last_action` 會記下原因，靜默退回下一節的軟停損停利頂著，不會讓整個
進場流程中斷。

---

## 4. 之後每一輪（60 秒）都在檢查什麼：三層止損防護網

系統一共設計了 3 道層級分明的停損機制：
- **第 1 層（券商 OCO）**：進場即掛在群益主機，斷網關機也能在券商端自動止損止盈（主力防線，見 §3）。
- **第 2 層（軟停損備援）**：本地輪詢監控，僅在第 1 層掛單失敗或無智慧單時主動送市價單補位（備援防線，見 §4a）。
- **第 3 層（風控硬斷腕）**：本地風控最高優先級，不論是否有 OCO，浮虧金額超限立即無條件強平（最後保險，見 §4b）。

`_tick_one()` 對每個有留倉的策略，每輪依序檢查：

### 4a. 持倉點數停損停利（軟機制，OCO 掛不成才會用到）

```
points = 現價 - 進場價（多單）或 進場價 - 現價（空單）

if points <= -100 且沒有真實 OCO 保護單頂著:
    觸發停損 → 送市價 FOK 平倉單
elif points >= 250 且沒有真實 OCO 保護單頂著:
    觸發停利 → 送市價 FOK 平倉單
```

有真實 OCO 頂著時（`state.protection_order_smart_key` 有值），這裡主動讓路，
不會兩邊搶著平倉。這個檢查**不管策略是否因其他原因被停止都會跑**，只要
`held_qty>0` 就繼續保護。

### 4b. 額外一層風控保險（NTD / 百分比虧損上限，無條件硬斷腕）

浮動損益觸及 `max_loss_ntd` 或 `max_loss_pct*initial_capital_ntd` 任一門檻，
**不論券商端是否有 OCO 智慧單頂著，都會無條件強制送出市價單平倉**——正常情況點數停損會先觸發，這層是防跳空、極端滑價或多口損失換算後超過帳戶能承受範圍的硬斷腕保險。**這個觸發也會停止策略**（下方 §4e 整理所有還會停用策略的情況）。

### 4c. 反向訊號出場

方向限定策略遇到反向訊號：有留倉就平倉出場（市價 FOK），沒有留倉維持
空手（不反手）。

### 4d. 累計已實現虧損風控

空手時如果 `realized_pnl_ntd` 已經連續虧到超過門檻，停止策略，避免虧損
策略無視情勢一直重新進場。

### 4e. 還會真的停用策略的情況（完整列表）

`reconcile_after_manual_close`（§5a）拿掉自動停止之後，**還是有好幾個地方
會停用策略**，都是「已知、需要人工核對」的情況，不是這次修掉的那種誤判：

| 觸發條件 | 說明 |
|---|---|
| 使用者手動按「停止」 | 有留倉時不會真的移除監控，繼續頂著停損停利直到平倉才完全停止 |
| §4b NTD/% 風控保險觸發 | 強制平倉後停止 |
| §4d 累計已實現虧損超過門檻 | 空手時檢查 |
| 委託回報失敗，但偵測到近期有相符的真實成交紀錄 | `_check_orphaned_fill` 抓到的不確定情況（進場/出場都有各自的分支），寧可停下來讓人核對 |
| 連續 `MAX_CONSECUTIVE_FAILURES`（3 次）下單失敗 | 結構性拒單不會因為重試自己好，停止並報錯，不要無聲一直失敗 |

**跟 §5a 對帳同步不一樣的地方**：上面這些都是「這一輪程式自己直接觀察到
的明確事件」（使用者按了按鈕、真的碰到風控門檻、委託回報明確失敗），不是
「拿一份可能過期的 broker 快照去推論」——這是拿掉 §5a 自動停止的判斷依據，
不是「乾脆都不停了」。

## 5. 對帳同步（不是異常處理，是例行同步）

`strategy_tick()` 每輪跑完所有策略的 `_tick_one()` 之後，**接著做兩件事**：

### 5a. `reconcile_after_manual_close()`

跟券商回報的實際淨部位比對，內部記的口數比 broker 還多就代表「這筆倉位在
別的地方被關掉了」（手動平倉，或 OCO 已經在券商端正常觸發——後者是預期
內、健康的結果，不是異常）：

- 剛進場（30 秒內）的部位先跳過，不比對——broker 的持倉快照有實測過的
  15 秒左右回報延遲，太早比對一定誤判。
- 偵測到不一致：**只同步內部記帳**（清空 `held_qty`/`held_direction`/
  `entry_price`），**不停止策略、也不撤保護單**。broker 回報的淨部位才是
  唯一真相，這裡只是讓內部記帳跟上；就算判斷錯了，頂多下一輪自己修正
  回來，不會有任何實際部位受影響。

### 5b. `reconcile_orphan_stop_orders()`

`held_qty==0` 但還記著保護單號的策略（可能是上面 5a 剛清空的，也可能是
軟停損停利自己平倉後忘了撤），過了獨立的 30 秒寬限期（從清零那一刻重新
起算，不是沿用進場時間）才真的去撤這張變成孤兒的保護單。

---

## 6. 一鍵平倉（手動、非自動）

儀表板「一鍵平倉」按鈕（`/api/positions/flatten`）會把 broker 回報的**所有**
持倉（不分策略）一次全部送市價平倉單，平倉後立刻呼叫一次 §5a 的對帳讓內部
記帳同步。沒有「只平掉某一筆」的按鈕。

**平倉安全防呆**：送出的委託全部嚴格指定 `new_close = 1（平倉）` + `trade_type = FOK`。若使用者剛在手機 App 手動平倉了、而量化系統快照延遲了幾秒才送出平倉單，券商主機會直接以「留倉部位不足」退單拒絕，**完全不會重複平倉或意外反手開新倉**。

## 7. 一張圖串起來

```
K棒收盤確認訊號
      │
      ▼（≤60 秒內偵測到）
市價單進場（FOK，用即時報價/備援估價）
      │
      ▼（entry_price > 0）
掛真實 OCO 保護單（-100 / +250）──掛失敗──▶ 靠 §4a 軟停損停利頂著
      │
      ▼
每 60 秒重複檢查：
  §4a 軟停損停利（OCO 有頂著就讓路）
  §4b NTD/% 風控保險
  §4c 反向訊號出場
  §4d 累計虧損風控（§4e 列表裡任一情況都可能停用策略）
      │
      ▼（不管哪個路徑平倉）
下一輪 §5a 對帳自動同步內部記帳（不停止、不撤單）
§5b 過寬限期後清掉真正的孤兒保護單
```
